# Design conformance

What the prototype designs, what the app builds, and where the two deliberately
disagree.

This exists because the design and the code are written in different places and
drift apart quietly. `scripts/check-design-sync.mjs` reads this file on every
build and fails when it goes stale: every screen the prototype defines must have
a row here, and every row claiming something is built must name a path that
exists. It cannot tell you whether a screen *looks* like its mock — that is a
person with both in front of them — but it can stop the ledger quietly becoming
fiction.

**Statuses.** `built` — the thing exists and does its job. `partial` — some of it
exists, and the note says which part is missing. `not-built` — designed, not
started; the note says which stage owns it, per `docs/build-plan.md`.

**Artboard.** Each screen row names the board it is drawn on in `docs/design/vibrant-canvas.html` (the
board's id, which the index at the top of that file links to), a comma-separated list where a screen has
more than one, or `none`. `none` is for a screen the canvas does not draw: Summary and sign-in, and the
screens not yet built. `check-design-sync` fails a screen with neither, or one naming a board that is not
in the file. Layout and hierarchy come from the board and values from `tokens.md` and `icons.md`
(CLAUDE.md); every visible difference between a screen as built and its board is a row in Departures,
`proposed` until the owner decides it.

Adding a screen to the prototype without adding a row here fails the build. That
is the point: the failure is a prompt to decide when it gets built, not busywork.

## Departures

Places the app does not follow the prototype or the canvas, and the reason it gave.
Each has a **Status**, because a departure is the owner's to accept and a reason
written down is not the same as a decision made:

- `unreviewed` — written by whoever built the screen, with a reason, and not yet
  looked at by the owner. It is not settled. A screen that differs from the canvas
  *because of* an unreviewed row differs by default and not by decision.
- `proposed` — new in the slice just finished, and put to the owner as a question
  at the end of the slice report. A departure goes in as `proposed`, never as
  `decided`: the call is the owner's.
- `decided` — the owner has looked at it and said which way it goes, and the row
  says what was decided. A decision to follow the canvas removes the row.

`scripts/check-design-sync.mjs` fails a row with no Status, or one that is not one of
these three.
